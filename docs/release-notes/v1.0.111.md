# v1.0.111 test candidate

Some valid embedded fonts appear in a PDF inventory as Type0/`cid` while their extracted bytes are ordinary name-keyed CFF. They previously stopped default text delivery or reached an unnecessary image fallback. A structurally qualified single CFF1 program now follows the existing source-preserving converter and exact original Unicode-to-glyph map, retaining editable text. CID-keyed ROS/FDArray/FDSelect programs, multiple fonts, malformed data and unverified character bindings do not qualify.

Failed font builds are matched to the original character program hash rather than a font-name spelling. Their original page, source xref and failure category are preserved; missing, mixed, conflicting or changed program evidence remains blocked. Existing Type3 and empty-stream/ActualText routes are preserved. Source font assets separately record the original PDF inventory format/type and their canonical program format.

The generated public CID-CFF fixture joins the existing real-Blender compatibility matrix. Its check requires requested native 3D font entities with positive extrusion and verified packed font bytes; generic completion or raster fallback cannot pass. The existing four matrix import cases remain in place.

Blender 3.1 stores a true round-stroke custom property as integer `1`. Both publication checks now recognize that exact legacy representation alongside boolean `True`; other numbers and truthy values remain rejected. Source, geometry, placement, ownership and rollback checks remain required.

This candidate does not resolve the separately observed Windows embedded-Python access-violation diagnostics. Those also occur in identity-only and earlier-version checks; no unsupported teardown fix or diagnostic suppression was added. GUI and rendered side-by-side PDF acceptance remain separate.
